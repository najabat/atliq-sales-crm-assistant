# Build decisions

The PRD says what the product does. This page records the choices the PRD left to the build, each with its reason and what it costs. The README points here.

Status on 11 October 2026. Najabat accepted every decision on this page. D5, D9 and D23 changed on 11 October after the Gemini free tier limits were checked. D12 to D14 were added in the afternoon. D15 to D18 and the change to D5, D7 and D9 came from the review of all artifacts later that day. D19 and D20 and the change to D16 and D17 came from the final review that night. D21 to D27 came from the reviews of the build pack on 9 October. Najabat decided the two open answer key labels on 9 October before sign off. His sign off is kept with the answer key, outside this repository.

| D17 | The next step date is the nearest firm due date on or after the reference date among the account's open items. A loose date sets nothing. The owed list is the record of every action and the CRM date only sums it up | The PRD said code sets the date and did not say how. The answer key already follows this rule on all 7 rows it requires. The second review on 8 October showed an account with only overdue work would look like it had no next action | A row with only loose items keeps an empty next step date and carries no flag. | D25 | Stricter matching in the scorer. Right account, lead ID and type or an accepted type. Repeats count as false alarms. A new CRM row fills only four fields. | D26 | Git-tracked files hold no dataset specifics. The cases the scorer and its tests need sit in the ignored `eval/cases.json`. | D27 | An accepted passage counts as right when the item is on an account the key links to its document. A firm date on an accepted passage must still match its label, or it counts as an invented date. Four regression tests cover this | Accepted, 9 Oct |

## D2 in detail, so the choice can be defended

| What the project needs | Browser storage with export | A shared database |
|---|---|---|
| An approval survives a page reload, PRD question OQ-14 | Yes | Yes |
| Who decided and when is recorded, FR-11 | Yes, in the browser, and it can be downloaded | Yes, in one place |
| The CRM working copy can be exported, FR-19 | Yes | Yes |
| A reviewer who opens the public link sees a full approval queue | Yes, every browser starts fresh | Only with a reset button or a copy for each visitor, which is more to build |
| Two sellers see each other's approvals | No | Yes |
| The cap of 40 notes a day holds across server restarts | No. The passcode and the key with no billing do | Yes |
| New accounts, secrets and failure points on demo day | None | One more of each |
| Build time on a one day build, my estimate | About one hour | About three hours |

The pilot is where a database earns its place, together with sign-in and the write-back to Kaizen. The PRD already puts all three after the capstone. Three small things keep that step cheap.

1. One storage module with six functions. Load, save a decision, undo, export, import a saved file and reset. The screens call only these.
2. Stable ids for items and changes, built from the file, the type and the quote. A new run keeps every decision whose target still exists.
3. A button on How it works that resets this browser, for the demo video and for any reviewer.

## How a paid key is fenced in, if one is used

1. Prepaid credit only, about 5 USD. Anthropic's help page says API use is paid from prepaid credits and the API stops when they run out. An optional spend limit of 5 USD in the Console is a second fence.
2. Auto reload stays off.
3. The key is never added to Vercel and never committed.
4. Five documents run first and the cost is shown before any full run. The spend guard refuses any call that could take the run past 4 USD, see D24.
5. Every key is deleted after grading.
